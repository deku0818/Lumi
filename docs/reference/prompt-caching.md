# Prompt Caching 参考

本文说明 Lumi 如何保持稳定请求前缀，以及缓存成本对模型、工具与压缩的影响。缓存优化不改变用户明确切换模型或更新 MCP 的行为。

---

## 核心原理：前缀匹配

Prompt 缓存依赖相同请求前缀：改动工具、系统提示词或早期历史，会缩短后续请求可复用的前缀。具体匹配与命中条件由服务端决定。

```
请求:  [A] [B] [C] [D] [E（新）]
缓存:  [A] [B] [C] [D]
                          ↑ 从这里开始才需要计算
```

因此应尽量保持请求前部稳定，将每轮动态信息放到消息尾部。

---

## 请求结构最佳排列

原则：**越稳定的内容越靠前，越容易变的内容越靠后。**

```
┌─────────────────────────────────┐
│  ① 静态系统提示词 & 工具定义     │  ← 全局不变，缓存断点
├─────────────────────────────────┤
│  ② 稳定项目上下文               │  ← 已读取的说明与历史
├─────────────────────────────────┤
│  ③ 对话历史消息                  │  ← 每轮追加，无需标记
├─────────────────────────────────┤
│  ④ 最新一轮消息                  │  ← 缓存断点
└─────────────────────────────────┘
```

---

## 缓存断点标记策略

Lumi 的 Anthropic 缓存统一使用 `cache_control: {"type": "ephemeral", "ttl": "1h"}`：

- `tool_call_chain` 保留静态 system prompt 的固定断点，并在绑定模型时开启历史缓存。
- 官方 `api.anthropic.com` 使用请求顶层 `cache_control`，由服务端自动移动消息末尾断点。
- 代理和 Anthropic 兼容端点由 `ReplayChatAnthropic` 将顶层参数转换为最后一个可缓存内容块的断点，复用 LangChain 的块选择函数。
- Graph 不再给最后两条消息手工添加标记；缓存参数仅用于构造请求，不写入原始历史，也不改动 thinking 或签名。
- 摘要链通过 `cache_history=False` 保持原有行为：仅固定系统断点，不启用消息尾部缓存。其他协议不注入 Anthropic 缓存参数。

当前依赖范围已支持此路径，无需升级 SDK。兼容端点转换使用
`langchain-anthropic` 的内部辅助函数，升级依赖时用 `tests/test_prompt_cache.py`
验证请求格式和历史不变性。请求格式正确不代表缓存命中；实际命中仍取决于
服务端支持、前缀一致性、最小 token 数和有效期。

参考：[LangChain 自动缓存](https://docs.langchain.com/oss/python/integrations/chat/anthropic#automatic-caching)、[Anthropic Prompt Caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。

## 动态信息处理

**不要**把时间戳等动态信息写在系统提示词里（每次变动 → 缓存全部失效）。

**正确做法**：通过对话消息中的 `<system-reminder>` 标签传递更新，保持系统提示词不变。

---

## 模型、工具与压缩

### 切换模型的成本

切换模型通常不能沿用原模型缓存。Lumi 将模型固化为会话属性，用户仍可明确切换；独立任务也可交给子代理，避免主会话反复更换模型。见 [会话模型](../architecture/model-switching.md)。

### 工具变更的成本

工具定义属于请求前缀，增减或修改会影响复用。Lumi 的 MCP 工具仍可动态更新，不能为保缓存而忽略新配置。Ultra 采用消息提醒表达状态，不因档位切换增删 Workflow 工具。

Lumi 当前没有 `ToolSearch` / `defer_loading` 工具延迟加载接口，不应将其他产品的方案当作已有能力。

### 压缩请求与缓存

摘要链尽量复用主对话的系统提示词和工具前缀，但不注入主链思考档位，Anthropic 也不启用消息尾历史缓存，因此不能保证命中主对话缓存。PTL 重试还可能剥离图片或丢弃早期轮次。参数与选材以 [压缩架构](../architecture/compact.md) 为准。

## 速查表

| 原则 | 做法 | 原因 |
|------|------|------|
| 内容排列 | 静态在前，动态在后 | 前缀匹配 |
| 缓存断点 | 只标在 system prompt 和对话末尾 | 滑动窗口 |
| 动态信息 | `<system-reminder>` 追加在消息中 | 不改系统提示词 |
| 切换模型 | 用户明确选择后切换，独立任务可用子代理 | 模型缓存通常不可复用 |
| 工具变更 | 接受配置更新，避免无意义抖动 | 工具是前缀一部分 |
| 状态切换 | 用工具本身建模 | 工具列表不变 |
| 上下文压缩 | 尽量复用稳定前缀，核对实际 usage | 摘要链与主链请求不完全相同 |

---

## 容易踩的坑

1. 在系统提示词中放时间戳 → 每次请求缓存失效
2. 工具定义顺序不确定（`dict` 遍历）→ 顺序变了等于前缀变了
3. 动态更新工具参数 → 工具定义变了，缓存失效
4. 将摘要链请求格式正确误当作已经命中主对话缓存
5. 忘记预留压缩缓冲区 → 上下文用满后没有空间

> **一句话总结**：把系统提示词和工具定义当作不可变的，把所有变化都推到对话消息的末尾。
